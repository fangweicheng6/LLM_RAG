# RAG 服务对接说明（生成开关 / 纯检索接入）

本服务可以作为两种角色使用：

1. **完整 RAG 问答**：检索 → 上下文选择 → LLM 生成回答（默认模式）；
2. **纯检索（chunk 供应方）**：只返回与问题相关的知识块，不生成回答，
   由外部系统用自己的 LLM 基于这些 chunk 生成最终答案。

两种角色由配置开关 `rag.generation.enabled`（configs/rag.yaml）控制，
三个前端（HTTP / Socket / MCP）共用同一套行为。

---

## 1. 开关：控制本服务的最终回答生成

编辑 `configs/rag.yaml`：

```json
{
  "rag": {
    "generation": {
      "enabled": false
    }
  }
}
```

- 修改后**需要重启服务进程**（settings 在进程启动时加载，没有文件热重载）。
- **本仓库当前默认 `false`**（对接形态：本服务只供 chunk，回答由外部系统的
  LLM 生成，见 `docs/MCP对接文档.md`）。
- 改回 `true` 即恢复内置生成，行为与旧版本完全一致。

### 关闭后的行为

| 入口 | 行为 |
| --- | --- |
| HTTP `POST /chat` | 不再调用生成 LLM；响应中 `answer` 为 `null`，`generation_enabled` 为 `false`，`answer_sources` 为 `[]`；相关 chunk 完整保留在 `selected_contexts` |
| Socket `{"cmd":"query"}` | 同上（与 HTTP 同源响应） |
| MCP `rag_chat` | `answer` 为 `null`、`generation_enabled` 为 `false`；证据仍在 `selected_contexts` |

同时，关闭生成后：

- 不再创建 generator 角色的 LLM 客户端（纯检索部署不需要该角色的模型配置）；
- **上下文选择器（selector）不受影响**，仍按其自己的开关
  `rag.context.selector.enabled` 运行——它是独立的一次 LLM 调用，
  负责选出最相关 chunk 并判断信息是否充分。若要做到**零 LLM 调用**，见第 5 节。
- **对评测的影响**：E2E 评测（`evaluation/rag_valide.py`，即 `run_benchmark_evaluation`
  的 `e2e` / `all` 分支）走的是同一条被开关控制的 `retriever.run` 管线 ——
  生成关闭时 `answer` 为 `null`，answer 相关指标按空答案记 0（其余指标如
  context_recall 正常计算，不会报错）。**要评估生成质量，请把开关置 `true`**。
  generation 专项基准（`--type generation`）直接调用生成器，不受影响。

## 2. 纯检索接口（任何模式下都可用，不生成回答）

即使 `rag.generation.enabled=true`，也可以直接用下面的纯检索接口拿 chunk：

| 入口 | 请求 | 说明 |
| --- | --- | --- |
| HTTP | `POST http://<host>:8000/search`，body `{"query": "..."}` | 新增接口，与 MCP `rag_search` 等价 |
| Socket | `{"cmd": "search", "text": "..."}` | 新增命令 |
| MCP | 工具 `rag_search(query=...)` | 一直存在 |

纯检索接口内部**不运行**上下文选择器与生成器，只走
Router → 多跳扩展 → 向量检索 → 词法混合 → 重排 → 候选池。

---

## 3. 响应字段契约

### 3.1 `POST /chat`（HTTP / Socket `cmd=query` / MCP `rag_chat` 同源）

```jsonc
{
  "query": "BUCK 电感如何计算？",
  "keywords": ["buck", "电感"],
  "domains": ["topology"],
  "router_domains": ["topology"],
  "router_enabled": false,
  "llm_chunk_selection_enabled": true,
  "generation_enabled": false,        // 本响应是否经过回答生成阶段
  "candidate_pool": [ /* 候选块，见 3.3 */ ],
  "selected_contexts": [ /* 选中的上下文块，见 3.3；关闭生成后这里就是你要的 chunk */ ],
  "selection_reason": "…",
  "context_sufficient": true,
  "missing_information": [],
  "expansion_history": [],
  "answer": null,                      // 生成开启时为字符串答案；关闭时为 null
  "answer_sources": []                 // 生成开启时为 [{label, chunk_id, source_file, section, location}]
}
```

检索未命中（确实没有相关 chunk）时另有一个 `retrieval_miss_reason` 字段，
`candidate_pool` / `selected_contexts` 为空数组，`answer` 在关闭生成时为 `null`。

> MCP `rag_chat` 的载荷是上表裁剪后的版本：字段为
> `answer / generation_enabled / context_sufficient / missing_information /
> router_domains / domains / selection_reason / sources / selected_contexts`，
> 其中 `selected_contexts` 最多 8 条、每条正文截断到 2000 字符；
> **需要完整正文请走 HTTP `/chat` 或 `/search`**。

### 3.2 `POST /search`（HTTP / Socket `cmd=search` / MCP `rag_search` 同源）

```jsonc
{
  "query": "BUCK 电感如何计算？",
  "keywords": ["…"],
  "domains": ["topology"],
  "router_domains": ["topology"],
  "router_enabled": false,
  "generation_enabled": false,        // 纯检索响应固定 false：本响应不经过生成阶段
  "candidate_pool": [ /* 3.3，重排后的相关块，最相关的在前 */ ],
  "selected_contexts": [],            // 纯检索不做上下文选择，固定为空
  "answer": "",
  "answer_sources": []
}
```

检索未命中（无任何相关块）时 `candidate_pool` 为空数组，并附
`retrieval_miss_reason` 字段；`answer` 固定为空串、`generation_enabled`
固定 `false`（纯检索语义，不随全局开关变化）。

> 注：MCP `rag_search` 的载荷是上表裁剪后的版本（与 HTTP/Socket 不同源直出）：
> 字段为 `query / router_domains / domains / count / candidates[...]`，
> 候选最多 20 条、每条 `text` 最多 2000 字符，且不含 `answer` /
> `generation_enabled` 等字段（对纯检索对接方无影响）。

### 3.3 chunk 元素结构（`candidate_pool` / `selected_contexts` 通用）

```jsonc
{
  "chunk_id": "DOC_xxx_0012_ABCD1234",
  "collection": "rag_topology",
  "document": "chunk 全文……",          // 解析后的原文，可直接作为 LLM 上下文
  "similarity": 0.91,                  // 开启 rerank 时=重排分（与 rerank_score 一致）；
                                       // 关闭 rerank 时为向量相似度（= 1 - distance）
  "distance": 0.09,
  "rerank_score": 0.91,                // 开启 rerank 时存在，优先用它排序
  "retrieval_source": "reranker",      // vector | lexical | reranker | same_section | …
  "metadata": {
    "source_file": "xxx.pdf",
    "relative_path": "topology/xxx.pdf",
    "domain": "topology", "subdomain": "…",
    "section_path": "第3章 > 3.2 …",     // 章节路径
    "page": 12, "page_end": 12,         // 页码（PDF）
    "sheet_name": null, "row_start": null,
    "content_type": "text", "title": "…"
  }
}
```

### 3.4 错误形态

- HTTP：引擎异常会以 FastAPI 500 返回（无 JSON 错误体）；
  检索未命中不报错，走 3.2 的空结果。
- Socket：逐请求捕获异常，返回 `{"error": "…"}`。
- MCP：异常转为 `ToolError`（协议层工具错误）。

## 4. 对接示例（外部 LLM 消费 chunk）

```python
import requests

RAG = "http://127.0.0.1:8000"

def retrieve(question: str, top_k: int = 6) -> list[dict]:
    """拿相关 chunk；/search 永远不生成，/chat 在开关关闭时 answer=null。"""
    r = requests.post(f"{RAG}/search", json={"query": question}, timeout=120)
    r.raise_for_status()
    data = r.json()
    pool = data["candidate_pool"]
    if not pool:                     # 未命中：data 里有 retrieval_miss_reason（/chat 路径）
        return []
    # 有 rerank_score 按它排，否则按 similarity 排
    pool = sorted(pool, key=lambda c: c.get("rerank_score") or c.get("similarity") or 0, reverse=True)
    return pool[:top_k]

def build_context(chunks: list[dict]) -> str:
    blocks = []
    for i, c in enumerate(chunks, start=1):
        m = c["metadata"]
        blocks.append(
            f"[C{i}] 来源: {m['source_file']} | 章节: {m.get('section_path','')} | 页: {m.get('page','')}\n"
            f"{c['document']}"
        )
    return "\n\n".join(blocks)

# —— 接你自己的 LLM ——
question = "BUCK 电感如何计算？"
chunks = retrieve(question)
context = build_context(chunks)
prompt = f"仅依据以下知识库内容回答问题，并标注引用 [C1][C2]…\n\n{context}\n\n问题：{question}"
# your_llm_chat(prompt) ...
```

引用/溯源：chunk 的 `chunk_id` 与 `metadata`（source_file / section_path / page）
就是定位信息；若需要与 `answer_sources` 相同的精简引用格式
（`label/chunk_id/source_file/section/location`），可自行用 `metadata` 拼出，
或直接读服务端 `ingestion/source_store.format_location(metadata)` 的同款规则。

## 5. 纯检索部署（零 LLM 调用、不需要 LLM_API_KEY）

查询链路上共有 4 个会调用 LLM 的位置：Router、multi-hop 子查询扩展、
Context Selector、最终回答生成。全部关闭：

```json
{
  "rag": {
    "generation": { "enabled": false },
    "context": { "selector": { "enabled": false } },
    "retrieval": { "multi_hop": { "enabled": false } }
  }
}
```

- `router.enabled` 默认已经是 `false`（全域检索）。
- 上表四项都关：整个查询链路不再有任何 LLM 调用，
  检索结果由向量相似度 + 词法 + 重排给出，`context_sufficient` 恒为 `false`
  （选择器关闭时不伪造“已确认充分”），对 chunk 供应场景无影响。
- `model.llm.*` / `LLM_API_KEY` 仍会被加载但不会发起网络调用。
- 注意：只关 `generation` 时，multi-hop / selector 仍可能调用 LLM（视各自开关）。

## 6. 常见问题

**Q: 我改了 rag.generation.enabled 为什么没生效？**
配置在进程启动时读取，重启 HTTP/Socket/MCP 服务后生效。

**Q: /chat 返回 `answer: null` 是出错了吗？**
不是。看 `generation_enabled`：为 `false` 表示服务端按配置不生成回答，
chunk 在 `selected_contexts` 中，属于预期行为；
若 `generation_enabled` 为 `true` 且 `answer` 非空，即常规问答响应。

**Q: 内部命令行（`python -m pipeline.retrieval.retriever "问题"`）会受影响吗？**
会。它与在线服务走同一段 `_run` 逻辑，同样遵循 `rag.generation.enabled`。

**Q: 评测结果里的 answer 会不会因为开关变化？**
会。E2E 评测（`rag_valide` / `--type e2e|all`）跑的是同一条受控管线：
开关关闭时 `answer` 为 `null`、answer 相关指标记 0（不会再报 metric_error，
其余指标正常）。要评测生成质量，把 `rag.generation.enabled` 置 `true` 再跑。
generation 专项基准（`--type generation`）不受开关影响。

**Q: MCP 里 `rag_chat` 和 `rag_search` 怎么选？**
要本服务的模型生成答案（且开关为开）用 `rag_chat`；
只要原始证据或服务端已关闭生成，用 `rag_search`
（或 HTTP `/search`、Socket `cmd=search`）。
