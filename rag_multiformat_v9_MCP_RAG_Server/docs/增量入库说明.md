# 增量入库说明

面向日常维护知识库的人。核心结论：**新增/修改/删除文件后，跑一条命令即可，
不需要清空向量库重建。**

```powershell
cd /d D:\RAG\rag_multiformat_v9_MCP_RAG_Server
python -m ingestion.ingest --incremental
```

---

## 1. 三种入库模式

| 命令 | 切片阶段 | 向量库阶段 | 什么时候用 |
| --- | --- | --- | --- |
| `python -m ingestion.ingest --incremental` | **只重新解析**新增/内容变化的文件 | 对账 | **日常更新**（推荐） |
| `python -m ingestion.ingest` | 重新解析**全部**文件 | 对账 | 首次入库；改过切片配置/代码后 |
| `python -m ingestion.embed_store --rebuild` | 不动 | **强制重新嵌入全部 chunk** | 换了 embedding 模型、怀疑向量库脏 |

三者共用同一条向量库写入路径（对账器），所以**结果一致**：向量库里恰好是索引
里的那些 chunk，多退少补。

> 「对账」= 比对「索引期望的 chunk 集合」与「向量库现有的 chunk 集合」，只嵌入缺的、
> 只删除多的。没变化时它会直接跳过，连 embedding 模型都不加载。

---

## 2. 日常操作

### 新增文件

```powershell
# 1. 先看一眼会发生什么（不写任何东西）
python -m ingestion.ingest --incremental --dry-run
# 2. 确认无误后执行
python -m ingestion.ingest --incremental
```

只有新文件会被解析。实测：知识库 190 个文件里新增 1 个，全程只解析那 1 个。

### 修改文件

同上。文件内容一变，`source_file_hash` 就对不上，该文件会被重新切片，
其旧 chunk 会被替换掉（同一路径 = 同一个 `document_id`）。

### 删除文件

同上。源文件从知识库移走后，它的 chunk 会**同时从索引和向量库删除**——
这是增量之前完全没有的能力。

### 重命名 / 移动文件

等同于「旧路径删除 + 新路径新增」。注意 `document_id` 由相对路径派生，
所以重命名会让该文件的所有 `chunk_id` 变化，引用过旧 `chunk_id` 的外部记录会失效。

---

## 3. 保护闸门

删除是唯一不可逆的动作，所以有两道闸：

| 情况 | 行为 |
| --- | --- |
| 扫描到 0 个文件、但索引里有文件 | **直接报错**，不发布。防止网络盘掉线/权限异常把库清空 |
| 单次删除文件占比 > `ingestion.incremental.max_delete_ratio`（默认 25%） | **报错**，需加 `--force-delete` |

不确定的时候先 `--dry-run`，它会列出将新增/重切/删除的文件清单。

---

## 4. 参数速查

| 参数 | 作用 |
| --- | --- |
| `--incremental` | 只重解析新增/变化的文件 |
| `--dry-run` | 只打印清单，不写任何东西（连临时文件都不建） |
| `--force-delete` | 允许单次删除超过阈值比例的文件 |
| `--resume` | 崩溃续跑：优先复用中断的 `.tmp`，没有则用已发布的索引 |
| `--rebuild`（`embed_store`） | 忽略库内现有内容，强制全部重新嵌入 |

`--resume` 与 `--incremental` 只差**基线取自哪里**：前者优先用中断的 `.tmp`
（没有则退回已发布的索引），后者用已发布的索引。装配逻辑完全共用——都按路径顺序输出、
都做同样的跨文件去重——所以**续跑结果与全量重跑逐字节相同**，中断期间增删改过的文件
也会被正确处理。两者互斥（选一个即可）。

用哪个：

- **上次跑挂了、想省掉重切的时间** → `--resume`（它能把崩溃前那份 `.tmp` 里已完成的
  文件直接复用，即使还没有发布过任何索引）
- **知识库更新了** → `--incremental`
- 两者的差别只是「从哪份产物里捡回已完成的部分」，效果都是「只重切需要重切的」。

## 5. 内部机制（维护者看）

### 索引 JSONL 是唯一事实源

`knowledge_base/processed/knowledge_index.jsonl` 的每一行都带着
`relative_path` 和 `source_file_hash`，所以「哪些文件变了」直接从这里推导，
没有额外的账本文件。增量发布的仍然是**整份索引**（未变文件的行逐字节复制、
变化文件的行重新生成），因此下游（词法检索 BM25、评估脚本、审计）的
「索引行集 == 当前语料全集」假设继续成立。

### sidecar 只是 advisory

`knowledge_index.jsonl.state.json` 记录切片口径指纹（`pipeline_fingerprint`）、
空产出文件名单和最近一次运行摘要。**随时可以删**——最坏后果是下次退化成
「以现有索引为基线 + 告警」。它不参与增量的事实判定。

指纹 = 切片代码版本号 + 索引 schema + `ingestion.*` 切片配置 + **切片 tokenizer**
（取自 `model.embedding.name`）+ 解析器版本（docling / rapidocr / openpyxl /
faster-whisper / pymupdf）。不一致时增量会拒绝，提示先全量重跑，避免新旧两种切片口径
混在同一份索引里。

指纹旁边还存了**原始输入项**（`fingerprint_parts`），所以能区分「指纹的覆盖范围更新了」
（键增删，不算口径变化，只告警）与「某个输入真的变了」（拒绝）。`.tmp` 也有一份伴随状态，
所以中断后改了切片配置再 `--resume` 同样会被拦下。

> **改任何影响 chunk 产出的逻辑，必须手动 `CHUNK_PIPELINE_VERSION += 1`**
> （在 `ingestion/index_state.py` 顶部）。

### 孪生分组（跨文件去重的正确性）

写侧有一层全局跨文件去重：同一份内容只保留先出现的那个。问题是索引里**只有幸存者**，
被挤掉的块无迹可寻。若 A 挤掉了 B 的同内容块，之后 A 被删掉——全量重跑会让 B 复活，
增量却认为 B「未变」，内容就**永久静默消失**了。

修法：每条 chunk 正文都以确定性上下文头 `文档《{文件名}》…` 开头，而去重指纹是对
整段正文归一化后算的，所以「跨文件指纹相同 ⟹ 归一化文件名相同」。于是按归一化文件名
分组，组内任一成员发生增/删/改，就把整组（仍存在的成员）重新解析。

这条推理依赖「每条 chunk 都带 CCH 上下文头」这个不变量，运行时会校验
（`index_state.cch_invariant_holds`）；一旦不成立就报错要求全量，不会静默损坏。

### 崩溃自愈

索引是 `.tmp` + 原子 `replace` 发布。sidecar 在发布**之后**写。中断后重跑，
会重新算出同一组「变化的文件」，没有任何状态需要手工清理。
向量库侧的对账同样幂等：写到一半失败，下一次运行会补齐。

续跑时怎么判断 `.tmp` 的最后一个文件有没有写完整：正常写入的 `.tmp` 旁边带一个
`complete` 标记（`with` 块退出即全部落盘）。**没有这个标记就说明进程是被原生杀掉的**
（写缓冲可能没落盘），最后一组整组丢弃重做——宁可多切一个文件，也不错用半截数据。

## 6. 回滚

- **`--incremental` 是可选开关**，不加就是原来的全量行为。
- 架构上可回滚，不依赖备份：`source_store` 只追加从不删除，索引原子发布，
  **向量库 100% 可以由「索引 + source_store」重建**。兜底一条命令：
  `python -m ingestion.embed_store --rebuild`（十几分钟量级，**不需要重新解析**）。
- 真删了东西想恢复：把文件放回知识库，再跑一次 `--incremental` 即可。

## 7. 常见问题

**Q：`--dry-run` 显示「新增 0，重切 0，删除 0，未变 189」是什么意思？**
索引与磁盘知识库完全一致，没有事情要做。这是刚入库完的正常状态。

**Q：为什么第一次跑增量会提示「索引缺少流水线指纹」？**
那份索引是在引入 sidecar 之前生成的。工具会以现有索引为基线继续（文件哈希就在行里，
判定是可靠的），并告警提醒。跑一次增量后指纹就记上了，之后是严格校验。
**若这期间改过切片配置或解析器版本，请先全量重跑一次。**

**Q：跑挂了，用 `--resume` 还是 `--incremental`？**
都行，`--resume` 通常更省：它能复用崩溃前那份 `.tmp` 里已切好的文件，**即使从未成功
发布过索引也有效**（首次入库跑挂就是这种情况）；`--incremental` 只能从已发布的索引里
回收。两者结果一致，都等于全量重跑。中断后**改过切片配置**会被拒绝，需要先全量。

**Q：服务要不要重启？**
要。词法索引（BM25）的进程内缓存会检查索引文件的 mtime/size 并自动重建，
但入库期间正在跑的查询仍可能读到旧语料。建议入库时停服务、完毕再启。

**Q：MCP 上能触发增量入库吗？**
可以。`rag_ingest` 管理工具（需 `service.mcp.expose_admin_tools=true`）支持
`incremental=true` 参数。

**Q：入库期间有别的进程在写吗？**
发布前会复核索引文件的基线（mtime + size），若被其他进程改过会放弃发布并提示重跑。
但这只是兜底，**不要并发跑两个 ingest**。
